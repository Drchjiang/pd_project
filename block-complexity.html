ICC2 Block 规模与复杂度评估指南

使用几何尺寸、Instance 数量、Macro、连接规模、Utilization、 Clock、Scenario、多电压域、时序和拥塞等指标，综合评价一个 ICC2 Block 的规模与物理实现难度。

本文同时说明两种使用场景： 只有读取权限，以及 同时拥有读取和写入权限。

1. 先理解四种不同操作

操作类型 典型命令 是否修改当前数据库 是否写入磁盘 只读 Block 是否适合
查询数据库 get_cells、 get_attribute、 sizeof_collection 否 否 适合
终端报告 report_qor、 report_utilization 否 通常否 适合
输出报告文件 redirect -file ... 否 是 必须输出到可写目录
修改当前会话 read_sdc、 read_def、 source、 placement/routing 命令 是 未必立即写入 不适合只读分析
保存数据库 save_block、 save_lib 把当前状态持久化 是 只读 Block 禁止
关键点： Linux 目录可写、ICC2 Library 可写、ICC2 Block 可写，是三个不同概念。 即使 Linux 目录可写，也不一定表示当前 Block 可以保存。

2. 只有读取权限时应该怎样做

查询 Block 属性、统计对象数量、执行原生报告，并在终端显示结果， 通常不需要 Block 写权限。

2.1 可以安全使用的命令

current_block
get_cells
get_nets
get_pins
get_ports
get_clocks
get_scenarios
get_power_domains
get_attribute
sizeof_collection
report_design
report_qor
report_utilization
report_reference
report_clocks
report_scenarios
report_timing
puts

expr

其中，Tcl 的 set 只是定义当前会话变量， 例如： 

set cells [get_cells -hierarchical *]

这不会修改 ICC2 Block，只是把查询结果保存在 Tcl 变量 cells 中。

2.2 不要在别人目录中写报告

如果当前 Linux 工作目录属于别人且不可写，不要执行： 

redirect -file report.rpt {
    report_qor
}

因为这会尝试在当前目录创建文件。 如果确实需要保存报告，应先切换到自己的可写目录。

切换 Linux 工作目录不会切换当前 ICC2 Block， 也不会改变 Block 的来源路径。

2.3 推荐启动方式

# Linux Shell 中执行
mkdir -p ~/icc2_block_analysis
cd ~/icc2_block_analysis

# 从自己的目录启动 ICC2
icc2_shell

然后以只读方式打开目标 Block。不同 ICC2 版本的打开选项可能不同， 应通过以下命令确认： 

help open_lib
help open_block
不要因为 Linux 文件权限显示为可读，就默认 ICC2 Block 已经以只读模式打开。 是否只读取决于实际的 Library/Block 打开方式和项目流程。

3. 同时拥有读写权限时应该怎样做

拥有写权限不代表必须修改设计。 如果目的只是评价 Block，仍建议优先使用只读查询命令。

3.1 只保存报告，不修改 Block

这是最安全、最常见的读写权限使用方式。 Block 本身不做修改，只把报告输出到可写目录。 

# 在 ICC2 中切换到自己的可写报告目录
set report_dir ~/icc2_reports
file mkdir $report_dir
cd $report_dir

puts "Current directory = [pwd]"
puts "Directory writable = [file writable [pwd]]"

输出单个报告：

redirect -file block_qor.rpt {
    report_qor
}

输出其他报告：

redirect -file block_utilization.rpt {
    report_utilization
}

redirect -file block_reference.rpt {
    report_reference
}

redirect -file block_clocks.rpt {
    report_clocks
}

redirect -file block_scenarios.rpt {
    report_scenarios
}
redirect -file 只负责保存命令输出， 不会因为写了报告文件就修改 ICC2 Block。

3.2 如果需要修改设计

如果你不仅要报告，还需要执行 placement、CTS、routing、ECO、 约束修改或 PG 修改，应采用下面的受控流程：

确认修改任务和授权 | v 确认当前 Library 和 Block 的来源 | v 创建独立副本或新的工作 Block | v 记录修改前的 QoR、Utilization 和 Timing | v 执行修改脚本 | v 执行检查和前后对比 | v 保存到新的 Block 名称 | v 确认无误后再决定是否更新正式版本

3.3 不建议直接覆盖原始 Block

即使你有写权限，也不建议第一次实验就直接覆盖 designer 的原始 Block。 更安全的方式是创建新版本或使用新的 Block 名称。

常见思路如下：

# 示例思路，实际语法应以当前 ICC2 版本帮助为准
set original_block [get_object_name [current_block]]

puts "Original block = $original_block"

# 修改前先保存为新的工作版本
# 不同 ICC2 版本和项目流程可能使用 save_block -as、
# copy_block 或项目封装命令。

help save_block
help copy_block

如果当前版本支持相应语法，项目中可能采用类似： 

# 仅为常见形式，执行前必须查看当前版本帮助
save_block -as block_name_analysis
save_block -as 是否可用、目标 Block 写到哪个 Library、 是否允许跨 Library 保存，取决于 ICC2 版本和项目 Library 结构。 执行前必须检查 help save_block。

3.4 修改前后的报告对比

修改前：

redirect -file before_qor.rpt {
    report_qor
}

redirect -file before_utilization.rpt {
    report_utilization
}

redirect -file before_timing_setup.rpt {
    report_timing -delay_type max -max_paths 50
}

redirect -file before_timing_hold.rpt {
    report_timing -delay_type min -max_paths 50
}

执行修改后，再生成对应的 after 报告：

redirect -file after_qor.rpt {
    report_qor
}

redirect -file after_utilization.rpt {
    report_utilization
}

redirect -file after_timing_setup.rpt {
    report_timing -delay_type max -max_paths 50
}

redirect -file after_timing_hold.rpt {
    report_timing -delay_type min -max_paths 50
}

在 Linux 中比较：

diff -u before_qor.rpt after_qor.rpt
diff -u before_utilization.rpt after_utilization.rpt

3.5 什么时候才保存 Block？

建议至少确认以下项目：

  • 脚本没有异常中断
  • Block 名称和目标 Library 正确
  • 关键 Cell、Net、PG 和约束没有意外丢失
  • QoR 没有明显恶化
  • Setup/Hold 没有出现不可接受的回退
  • Utilization 和 congestion 没有异常上升
  • 项目允许写入该 Block

确认后才执行项目规定的保存命令：

# 执行前确认当前 Block
current_block

# 查看当前版本的准确语法
help save_block
help save_lib

# 按项目流程保存
save_block
不要在不清楚影响范围时随意执行 save_lib。 它可能涉及整个 Design Library，而不仅仅是当前 Block。

4. Block 复杂度应该评价哪些指标

几何规模

  • Block 宽度、高度和面积
  • Core 宽度、高度和面积
  • 不规则边界
  • 狭窄放置和布线区域

逻辑规模

  • Leaf Instance 数量
  • Standard Logic Cell 数量
  • Sequential Cell 数量
  • Combinational Cell 数量

物理规模

  • Hard Macro 数量
  • Macro 面积和分布
  • Physical-only Cell 数量
  • Blockage 和 Macro Channel

连接规模

  • Net 数量
  • Pin 数量
  • Top-level Port 数量
  • 高扇出 Net 和 Pin Density

时序复杂度

  • Clock 数量
  • Generated Clock
  • Scenario 数量
  • WNS、TNS 和违例端点

物理实现难度

  • Utilization
  • Congestion
  • Macro 周边通道
  • DRC 和 Pin Access

多电压复杂度

  • Power Domain 数量
  • Voltage Area 数量
  • Level Shifter 和 Isolation
  • Power Switch、AON 和 Retention

运行资源复杂度

  • Mode 和 Corner 数量
  • MCMM Scenario 数量
  • 数据库对象数量
  • 内存和运行时间

7. Block 和 Core 的尺寸

7.1 报告 Block 的宽度、高度和外接面积 
set blk  [current_block]
set bbox [get_attribute $blk bbox]

set llx [lindex $bbox 0 0]
set lly [lindex $bbox 0 1]
set urx [lindex $bbox 1 0]
set ury [lindex $bbox 1 1]

set width  [expr {$urx - $llx}]
set height [expr {$ury - $lly}]
set area   [expr {$width * $height}]

puts "Block name   = [get_object_name $blk]"
puts "Block bbox   = $bbox"
puts "Block width  = $width um"
puts "Block height = $height um"
puts "BBox area    = $area um^2"
如果 Block 是 L 形、阶梯形或其他不规则多边形， width × height 只是外接矩形面积， 不等于真实多边形面积。
7.2 报告 Core 的宽度、高度和外接面积

当前环境中应通过 get_core_area 获取 Core， 不使用不存在的 Block core_bbox 属性。 

set core_obj  [get_core_area]
set core_bbox [get_attribute $core_obj bbox]

set llx [lindex $core_bbox 0 0]
set lly [lindex $core_bbox 0 1]
set urx [lindex $core_bbox 1 0]
set ury [lindex $core_bbox 1 1]

set width  [expr {$urx - $llx}]
set height [expr {$ury - $lly}]
set area   [expr {$width * $height}]

puts "Core bbox   = $core_bbox"
puts "Core width  = $width um"
puts "Core height = $height um"
puts "Core area   = $area um^2"

8. Instance 分类统计

8.1 All、Hierarchical 和 Leaf Instance

全部 Cell Instance

set all_cells [get_cells -quiet -hierarchical *]

puts "All cell instances = \
[sizeof_collection $all_cells]"

Hierarchical Instance

set hier_cells \
    [get_cells -quiet -hierarchical * \
    -filter {is_hierarchical == true}]

puts "Hierarchical instances = \
[sizeof_collection $hier_cells]"

Leaf Instance

set leaf_cells \
    [get_cells -quiet -hierarchical * \
    -filter {is_hierarchical == false}]

puts "Leaf instances = \
[sizeof_collection $leaf_cells]"
Leaf Instance 通常仍可能包含标准单元、Hard Macro 和 Physical-only Cell，因此不能直接等同于标准逻辑 Cell 数量。
8.2 Hard Macro 和 Physical-only Cell

Hard Macro

set hard_macros \
    [get_cells -quiet -hierarchical * \
    -filter {is_hard_macro == true}]

puts "Hard macros = \
[sizeof_collection $hard_macros]"

Hard Macro 可能包括：

  • SRAM、ROM、Register File
  • PLL、模拟 IP
  • PHY、SerDes
  • 其他固定物理尺寸的 Macro

Physical-only Cell

set physical_cells \
    [get_cells -quiet -hierarchical * \
    -filter {is_physical_only == true}]

puts "Physical-only cells = \
[sizeof_collection $physical_cells]"

可能包括：

  • Filler
  • Tap Cell
  • Endcap / Boundary Cell
  • Decap
  • 部分 Tie Cell 或 Spare Cell
is_hard_macro 和 is_physical_only 是否可用， 取决于 ICC2 版本、Library 和当前数据库状态。

如果属性报错，先查看可用属性：

list_attributes -application -class cell
8.3 Sequential、Combinational 和标准逻辑 Cell

Sequential Cell

set seq_cells \
    [get_cells -quiet -hierarchical * \
    -filter {is_sequential == true}]

puts "Sequential cells = \
[sizeof_collection $seq_cells]"

Combinational Cell

set comb_cells \
    [get_cells -quiet -hierarchical * \
    -filter {is_combinational == true}]

puts "Combinational cells = \
[sizeof_collection $comb_cells]"

近似标准逻辑 Cell

set std_logic_cells \
    [get_cells -quiet -hierarchical * \
    -filter {
        is_hierarchical == false &&
        is_physical_only == false &&
        is_hard_macro == false
    }]

puts "Standard logic cells = \
[sizeof_collection $std_logic_cells]"
Sequential Cell 数量通常可粗略反映 Clock Sink 数量、 CTS 规模、Clock Power 和 Hold 修复压力。

9. Net、Pin 和 Port 统计

set all_nets  [get_nets  -quiet -hierarchical *]
set all_pins  [get_pins  -quiet -hierarchical *]
set all_ports [get_ports -quiet *]

puts "Nets  = [sizeof_collection $all_nets]"
puts "Pins  = [sizeof_collection $all_pins]"
puts "Ports = [sizeof_collection $all_ports]"
指标 代表意义 数量高时的可能影响
Net Instance 和 Port 之间的逻辑连接 布线数量、数据库规模和运行时间增加
Pin Cell 的输入、输出、Clock 和控制 Pin Pin Density、Pin Access 和局部拥塞增加
Port Block 对外接口 边界布线和 Pin Placement 更复杂
两个 Block 的 Instance 数量相近时， Pin 数量更多、平均 Pin/Instance 更高的 Block， 通常具有更大的布线压力。

10. Utilization 的解读

report_utilization

重点关注：

  • Utilization Ratio
  • Total Capacity Area
  • Total Area of Cells
  • Excluded Area
  • Macro 和 Blockage 对可放置面积的影响
全局 Utilization 一般性评价 主要风险
< 60% 通常比较宽松 仍需检查 Macro 通道和 Pin Density
60%～70% 常见的中等水平 需要检查局部热点
70%～80% 放置和 ECO 空间开始紧张 合法化、拥塞和 Timing Closure 风险增加
80%～85% 高密度 Routing、DRC 和 ECO 风险较高
> 85% 通常属于高风险 是否可实现高度依赖工艺和 Floorplan
以上只是经验范围，不是项目签核标准。 全局 Utilization 不高，并不代表局部区域没有严重拥塞。

12. 多电压复杂度

set power_domains [get_power_domains -quiet *]

puts "Power domain count = \
[sizeof_collection $power_domains]"

puts "Power domains = \
[get_object_name $power_domains]"

还应检查：

  • Voltage Area 数量和形状
  • Level Shifter 数量和位置
  • Isolation Cell 数量
  • Retention Cell
  • Always-on Cell

13. 一键生成 Block 基础摘要

以下 Tcl 只查询当前 Block 并输出到终端， 不写文件、不保存 Block，也不修改设计。

脚本使用 catch 处理版本和属性差异。 某项查询失败时显示 N/A，而不是中断整个脚本。 

# ============================================================
# ICC2 READ-ONLY BLOCK COMPLEXITY SUMMARY
# 只查询并输出到终端，不修改或保存设计
# ============================================================

proc print_collection_count {label command} {
    if {[catch {uplevel 1 $command} objects]} {
        puts [format "%-30s : N/A" $label]
    } else {
        puts [format "%-30s : %d" \
            $label [sizeof_collection $objects]]
    }
}

puts "============================================================"
puts "ICC2 BLOCK COMPLEXITY SUMMARY"
puts "============================================================"

# ------------------------------------------------------------
# Current block
# ------------------------------------------------------------

set blk [current_block]

if {[catch {get_object_name $blk} block_name]} {
    set block_name "N/A"
}

puts [format "%-30s : %s" "Block name" $block_name]

# ------------------------------------------------------------
# Block dimensions
# ------------------------------------------------------------

if {[catch {get_attribute $blk bbox} block_bbox]} {
    puts [format "%-30s : N/A" "Block bbox"]
    puts [format "%-30s : N/A" "Block width"]
    puts [format "%-30s : N/A" "Block height"]
    puts [format "%-30s : N/A" "Block bbox area"]
} else {
    set llx [lindex $block_bbox 0 0]
    set lly [lindex $block_bbox 0 1]
    set urx [lindex $block_bbox 1 0]
    set ury [lindex $block_bbox 1 1]

    set block_width  [expr {$urx - $llx}]
    set block_height [expr {$ury - $lly}]
    set block_area   [expr {$block_width * $block_height}]

    puts [format "%-30s : %s" \
        "Block bbox" $block_bbox]

    puts [format "%-30s : %.4f um" \
        "Block width" $block_width]

    puts [format "%-30s : %.4f um" \
        "Block height" $block_height]

    puts [format "%-30s : %.4f um^2" \
        "Block bbox area" $block_area]
}

# ------------------------------------------------------------
# Core dimensions
# ------------------------------------------------------------

if {[catch {
    set core_obj  [get_core_area]
    set core_bbox [get_attribute $core_obj bbox]
}]} {
    puts [format "%-30s : N/A" "Core bbox"]
    puts [format "%-30s : N/A" "Core width"]
    puts [format "%-30s : N/A" "Core height"]
    puts [format "%-30s : N/A" "Core bbox area"]
} else {
    set cllx [lindex $core_bbox 0 0]
    set clly [lindex $core_bbox 0 1]
    set curx [lindex $core_bbox 1 0]
    set cury [lindex $core_bbox 1 1]

15. 如何综合判断 Block 的复杂程度

指标 复杂度增加的表现 主要影响 注意事项
Leaf Instance 数量增加 Placement、优化和运行时间增加 应排除 Physical-only Cell
Sequential Cell FF/Latch 数量增加 CTS、Hold 和 Clock Power 压力增加 还需考虑 Clock Domain 数量
Hard Macro 数量或面积增加 Floorplan、通道、PG 和拥塞更复杂 位置和 Pin 分布比单纯数量更重要
Pin 数量 Pin/Instance 比例提高 Pin Access 和 Routing Demand 增加 局部 Pin Density 比总数更重要
Utilization 可用空间减少 合法化、Routing 和 ECO 难度增加 必须结合局部 Utilization
Clock Clock Domain 和 Generated Clock 增加 CTS、CDC 和跨时钟分析更复杂 还需考虑 Sink 和 Clock Mux
Scenario Mode/Corner 组合增加 MCMM 分析和优化时间增加 注意哪些 Scenario 处于 Active 状态
Power Domain Voltage Domain 增加 LS、ISO、PSW、AON 和 PG 更复杂 还要看 Voltage Area 形状
Congestion Hotspot 和 Overflow 增加 Routing、Timing、SI 和 DRC 风险增加 重点检查 Macro Channel 和 Pin Access
WNS/TNS 负值扩大、违例端点增加 Timing Closure 难度增加 必须确认 PVT、OCV 和 Clock 状态

16. 常见误区

误区一： Instance 多的 Block 一定更难实现。
实际上 Macro、Pin Density、Clock、Power Domain 和 Congestion 都会显著影响实现难度。
误区二： Leaf Cell 数量就是标准单元数量。
Leaf Cell 可能包含 Macro、Filler、Tap、Endcap 和 Decap。
误区三： 全局 Utilization 不高就不会拥塞。
Macro 周边、狭窄通道、Voltage Area 边界和高 Pin Density 区域 仍可能出现严重拥塞。
误区四： 有写权限就可以直接修改原始 Block。
写权限只是技术条件，是否允许修改还取决于项目授权和版本管理规则。
误区五： source 只是打开 Tcl 文件。
实际上 source 会执行脚本中的全部命令， 可能修改约束、对象属性或物理数据库。
误区六： 执行了修改但没有 save_block，就完全没有影响。
修改虽然可能尚未写入磁盘，但当前 ICC2 会话中的数据库状态已经改变， 后续报告和操作都会基于修改后的状态。

17. 最推荐的工作流程

只有读取权限

  1. 从自己的可写目录启动 ICC2。
  2. 以只读方式打开目标 Library 和 Block。
  3. 执行一键统计脚本。
  4. 执行 report_qor、report_utilization 等原生报告。
  5. 结果只显示在终端，或者输出到自己的可写目录。
  6. 不要执行修改、导入和保存命令。

同时拥有读写权限，但只做评价

  1. 仍然优先使用查询和报告命令。
  2. 在自己的报告目录中保存报告。
  3. 不需要执行 save_block。
  4. 保存报告不会修改 Block。

同时拥有读写权限，并且需要修改设计

  1. 确认项目授权和目标 Block。
  2. 创建独立工作副本或新版本 Block。
  3. 保存修改前的 QoR、Timing、Utilization 和关键统计。
  4. 执行修改脚本。
  5. 检查错误、Timing、Congestion、DRC 和设计完整性。
  6. 生成修改后的报告并与修改前比较。
  7. 确认目标 Library 和 Block 名称正确。
  8. 按照项目流程保存新的 Block 版本。
  9. 不要在未确认时覆盖原始正式 Block。
实用结论： 第一轮评价建议使用 report_qor、 report_utilization、 report_reference 和一键统计脚本；第二轮再分析 Timing、Congestion、Clock、 Scenario 和多电压结构。
